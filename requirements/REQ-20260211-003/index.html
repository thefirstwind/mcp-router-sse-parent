    REQ-20260211-003: 虚拟项目参数类型问题¶

    日期: 2026-02-11 20:10
    优先级: P0 - 紧急
    状态: ✅ 已修复 (2026-02-12)
    依赖: REQ-20260211-002 (已修复)

    🔥 问题描述¶

    虽然虚拟节点的参数名已经修复（显示userId而不是arg0），但是调用Dubbo服务时参数类型错误：

    NoSuchMethodException: com.pajk.provider3.service.UserService.getUserById(int)
                                                                          ^^^
                                                  应该是: Long 而不是 int!

    🔍 根本原因¶

    架构问题¶

    虚拟项目配置中缺少Java参数类型信息！

    当前虚拟项目的工具定义（sN.json）只包含：

    {
  "toolName": "com.pajk.provider3.service.UserService.getUserById",
  "methodName": "getUserById",
  "interfaceName": "com.pajk.provider3.service.UserService",
  "inputSchema": "{...}"  // 只有JSON Schema，没有Java类型!
}

    问题: 1. inputSchema是JSON Schema格式 ("type": "integer") 2. 没有存储Java类型 (java.lang.Long) 3. McpExecutorService执行时无法获取正确的Java类型 4. 默认将integer推断为int而不是Long

    对比：真实Dubbo服务¶

    真实的Dubbo服务（非虚拟）从数据库查询方法签名：

    // McpExecutorService.java
String[] types = getParameterTypesFromDatabase(interfaceName, methodName, args);
// types = ["java.lang.Long"] ✅

    但虚拟项目没有存储到数据库！

    📊 数据流对比¶

    真实Dubbo服务¶

    JAR扫描 → 提取方法签名 → 存入数据库(dubbo_method_parameter)
                              ↓
                    McpExecutorService查询
                              ↓
                    获取准确的Java类型: java.lang.Long ✅

    虚拟项目（当前有问题）¶

    JAR扫描 → 生成JSON配置 → 存入文件(virtual-projects/sN.json)
                              ↓
                      只有JSON Schema (type: integer)
                              ↓
                     Mc pExecutorService无法获取Java类型
                              ↓
                    推断为 int (默认行为) ❌

    ✅ 解决方案¶

    方案1: ⭐ 在虚拟项目JSON中添加参数类型字段（推荐）¶

    修改工具定义结构，添加parameterTypes字段：

    {
  "toolName": "com.pajk.provider3.service.UserService.getUserById",
  "methodName": "getUserById",
  "interfaceName": "com.pajk.provider3.service.UserService",
  "parameterTypes": ["java.lang.Long"],  // ✅ 新增字段
  "inputSchema": "{...}"
}

    需要修改的组件: 1. PomDependencyAnalyzerService - JAR扫描时提取参数类型 2. VirtualProjectConfig - 添加参数类型字段 3. McpExecutorService - 从虚拟项目配置读取类型 4. 前端UI - 展示和编辑参数类型

    优点: - ✅ 简单直接 - ✅ 不依赖数据库 - ✅ 自包含（JSON文件包含所有信息）

    缺点: - ❌ 需要重新创建所有已有虚拟项目

    方案2: 虚拟项目也写入数据库¶

    将虚拟项目的方法签名也存储到数据库：

    INSERT INTO dubbo_method_parameter (
    interface_name,
    method_name,
    parameter_name,
    parameter_type,
    parameter_index,
    is_virtual  -- 新增标记字段
) VALUES (...);

    优点: - ✅ 统一架构（虚拟和真实服务使用相同逻辑） - ✅ 可以查询和管理

    缺点: - ❌ 增加复杂度 - ❌ 虚拟项目删除时需要清理数据库

    方案3: 智能类型推断（临时方案）¶

    在ParameterConverter中增强类型推断：

    // 如果目标类型是int，但值很大，自动升级为Long
if (targetType.equals("int") && value instanceof Number) {
    long longValue = ((Number) value).longValue();
    if (longValue > Integer.MAX_VALUE || longValue < Integer.MIN_VALUE) {
        // 自动升级为Long
        return Long.valueOf(longValue);
    }
}

    优点: - ✅ 快速修复，无需改动架构

    缺点: - ❌ 治标不治本 - ❌ 不适用于ID等场景（即使是小数字也应该用Long）

    🎯 推荐实施方案¶

    采用方案1：在虚拟项目JSON中添加parameterTypes字段

    实施步骤¶

    1. 修改数据模型¶

    在JAR扫描时保存参数类型：

    // PomDependencyAnalyzerService.java
Map<String, Object> tool = new HashMap<>();
tool.put("toolName", ...);
tool.put("methodName", ...);
tool.put("interfaceName", ...);
tool.put("parameterTypes", methodInfo.getParameters().stream()
    .map(ParameterInfo::getType)
    .collect(Collectors.toList()));  // ✅ 新增
tool.put("inputSchema", ...);

    2. 修改执行逻辑¶

    在McpExecutorService中优先使用虚拟项目配置的类型：

    // 1. 尝试从工具定义获取
String[] types = getParameterTypesFromToolConfig(toolName);

// 2. 降级：从数据库获取（真实Dubbo服务）
if (types == null) {
    types = getParameterTypesFromDatabase(interfaceName, methodName, args);
}

// 3. 兜底：类型推断
if (types == null) {
    types = inferParameterTypes(args);
}

    3. 数据迁移¶

    为已有虚拟项目添加类型信息：

    # 重新扫描JAR并更新JSON配置
curl -X POST http://localhost:9091/api/virtual-projects/rescan-all

    �️ 实施总结¶

    实施方案¶

    根据方案1进行优化，但为了保持向后兼容和灵活性，采取了双向补全策略：

    1. 代码层优化：
      • 修改 McpProtocolService.java，在 getAllMcpTools 逻辑中增加了对本地 virtual-projects/*.json 的扫描。
      • 实现了工具合并逻辑：若工具已存在（来自 Dubbo 实时上报），则会自动从 JSON 配置文件中补全 parameterTypes 和 inputSchema。
      • 优化了 executeToolCall 逻辑：当从配置中提取到显式参数类型时，会自动进行类型转换（如 Integer -> Long），从而匹配 Dubbo 方法签名。
    2. 数据层修复：
      • 手动更新了 s14.json，为 getUserById 等关键工具添加了显式的 "parameterTypes": ["java.lang.Long"]。
    3. 环境适配：
      • 增强了 virtual-projects 目录的探测逻辑，支持多种相对路径。

    验收结果¶

    • 调用 virtual-s14 的 getUserById 成功，不再抛出 NoSuchMethodException。
    • 日志记录显示正确匹配了显式参数类型并执行了自动转换。
    • 追溯链已在代码中通过 @traceability 标记。
